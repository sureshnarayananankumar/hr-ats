# Demo Data

A realistic dataset for demonstrations, screenshots and manual testing.

Generated by `backend/prisma/seed-demo.ts`, which is **separate from**
`prisma/seed.ts` (the reference-data seed). It is additive and leaves
all existing accounts untouched.

## Commands

```powershell
cd D:\HR-ATS\backend

npm run seed:demo          # add demo data alongside what exists
npm run seed:demo:reset    # remove previous demo data first, then add
```

Both require `SEED_DEFAULT_PASSWORD` in `.env`.

### Removing demo data

```powershell
npm run seed:demo:reset
```

Demo records are identifiable and removed cleanly:

- **Demo users** — email ends in `@demo.hr-ats.local`
- **Demo jobs** — `requirementCode` starts with `JR-DEMO-`

Everything else, including your staff accounts, is left alone.

## What it deliberately does not touch

The seven staff accounts and two original sample candidates keep their
ids, roles and password hashes:

```
superadmin@hr-ats.local      hr.admin@hr-ats.local
recruiter@hr-ats.local       recruiter2@hr-ats.local
manager@hr-ats.local         interviewer@hr-ats.local
interviewer2@hr-ats.local    candidate1@example.com
                             candidate2@example.com
```

Verified after generation: all nine present, all `ACTIVE`, all password
hashes unchanged, and `POST /api/auth/login` still returns `200`.

Demo candidates sign in with the **same password** as the staff
accounts, so you can log in as any of them to see the candidate portal
populated.

## How the data is shaped

### Jobs

58 requisitions built from 38 role templates across all 14 departments —
engineering, QA, data, security, product, PMO, IT, sales, marketing,
customer success, finance, HR, legal and operations.

Each carries a coherent skill stack (a DevOps role asks for Kubernetes
and Terraform; a finance role asks for IFRS and SAP), a sensible
seniority band, and a salary range consistent with that band.

Statuses are distributed as a real board would be:

```
29 published · 7 closed · 6 draft · 5 pending approval
 5 approved  · 4 on hold · 2 cancelled
```

Locations span Muscat, Sohar, Salalah, Dubai, Abu Dhabi, Doha,
Bengaluru, Hyderabad and remote.

### Candidates

242 profiles with names weighted toward the markets actually recruited
from — Oman and the wider Gulf, India, and a smaller international
cohort. Each has experience, current role and employer, education from a
real-world university list, notice period, salary expectation and a
skill set matched to their discipline.

### Applications

Distributed through a funnel that narrows the way a real one does: many
sit at early stages, rejections dominate the middle, and only a handful
reach offer and hire.

Every application has a full status history — one row per stage actually
traversed, with the acting user, timestamp and time spent in the
previous stage. That is what makes the time-to-hire and stage-duration
reports return real numbers.

### Interviews and feedback

318 interviews across technical, HR and final rounds, with panels drawn
from the interviewer accounts. 210 structured scorecards, where
candidates who progressed score higher than those who did not — so the
recommendation distribution is not random noise.

### Offers and onboarding

44 offers in sent, accepted and declined states, each with an approval
record and full status history. Accepted offers create onboarding
records with the ten-task checklist, at realistic completion levels.

## Design decisions worth knowing

**Deterministic.** A fixed RNG seed means repeated runs produce the same
shaped dataset, so screenshots and bug reports are reproducible.

**`vacanciesFilled` is reconciled, not invented.** After generation it
is recalculated from the actual number of `HIRED` applications and
capped at approved headcount — otherwise the dashboard's "open
positions" figure would be fiction.

**The duplicate-application guard is respected.** No candidate ever
holds two `ACTIVE` applications for the same job. Terminal applications
have `activeJobKey` set to `NULL`, which releases the unique index, so
re-application after rejection remains possible — exactly as in
production.

**One password hash, reused.** Argon2id takes roughly 100 ms per hash by
design. Hashing 242 demo candidates individually would add ~25 seconds
for no benefit, so the hash is computed once and reused. Real accounts
created through the API are always hashed individually.

## Test artifacts

`scripts/smoke-test.sh` creates a "Smoke Test Engineer" requisition each
time it runs. These are functional test artifacts, not demo content, and
they clutter the careers portal.

```powershell
cd D:\HR-ATS\backend
node scripts/clean-test-artifacts.mjs           # dry run
node scripts/clean-test-artifacts.mjs --delete  # remove them
```

Scope is deliberately narrow: it matches only requisitions titled
"Smoke Test Engineer" and deletes their dependent rows in
foreign-key-safe order.

## Branding

The careers portal, application shell, sign-in pages and candidate
portal use the Business Gateways wordmark from
`frontend/public/bgi-logo.svg`, rendered through
`frontend/src/components/ui/Logo.tsx`.

The asset is a wide wordmark (800×199), so `Logo` takes a `width` and
derives height from it — setting both would distort the mark. In dark
mode a CSS filter inverts it, since the supplied artwork is dark-on-
transparent and would otherwise vanish against the sidebar.

Re-apply branding after any UI refactor with:

```powershell
node scripts\apply-branding.mjs
```

It is idempotent and reports which edits applied.
